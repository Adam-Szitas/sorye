One platform, explicit domain rules

Verified in code

SUSM has a substantial backend

Angular 20 calls Actix routes. MongoDB database susm contains a company collection whose documents include users and projects; object and checklist operations update this domain. Dedicated feedback collections also exist.

Replacing the backend with a generic document-write event would discard authorization and business rules already embedded in those handlers.

Recommended design

Move a domain module, preserve its contract

Define a separate susm domain in Rodrigo behind typed operations. Reuse and port SUSM validation and permissions rather than exposing raw MongoDB queries. Hub authenticates, checks the integration grant and signs the call.

During migration, SUSM-BE remains the sole writer for domains not yet cut over. A domain switches to Rodrigo only after parity and failure checks pass.

Interactive journey requires JavaScript

SUSM inside the Sorye workspace

Proposed frontend integration · not implemented

SUSM can become a normal Sorye workspace app: open it from the launcher, keep a project open beside Notes or Drive, and return to it without losing the current view. Its Angular UI can remain in its own repository and build pipeline. The backend migration described above and this frontend integration are separate deliverables.

Sorye launcher→Catalog and access check→Load SUSM remote→Mount Angular into a workspace pane

One UI, two entry points

Inside Sorye: a remote exports ./mount, using Sorye’s container and kernel context. SUSM shows project tools; the Hub top bar provides shared navigation and language selection.

Standalone: the existing Angular bootstrap remains an entry point with its own page chrome and Sorye login. Public object and checklist-share pages stay reachable without opening the workspace shell.

Both entries reuse the same domain components and service interfaces. Avoid maintaining a second copy of the SUSM application.

Angular does not need a React rewrite

Introduce a mount adapter around an embedded Angular root. Create an application environment, render into the supplied element, connect a framework-neutral kernel adapter and return a cleanup function. Angular supports programmatic host-element mounting through createApplication and createComponent.

The federation wrapper must match Hub’s actual async loading and synchronous mount/cleanup contract. Do not expose an unresolved Angular bootstrap promise as the cleanup function; handle cancellation if the pane closes during bootstrap. Confirm APIs against SUSM’s installed Angular 20 version during implementation.

What the developer changes
  1. Register SUSM again as an active app. SUSM is currently retired in Sorye. Review the retired-ID handling, catalog ID/slug, access and subscription policy before registering the remote. Add its landing page, translations, remote override and deployment wiring.
  2. Add an embedded root and mount entry. Keep standalone login, marketing pages and public shares out of the mounted workspace root. Build a compatible remote entry exposing ./mount; Angular’s current standalone build is not already a federation remote.
  3. Add a Sorye adapter to SUSM services. Embedded requests use same-origin Hub APIs and the existing Hub session. Standalone requests use the approved Sorye login flow. The server derives identity and workspace; browser kernel context is UI context, not authorization proof.
  4. Separate routing ownership. Hub owns browser history and workspace navigation. SUSM owns its project/object/tab route in app-local state, with an explicit bridge for deep links and back/forward. Its current root routes such as /projects and /admin must not take over Hub’s router. Do not attach a second unrestricted browser-history router.
  5. Keep private state local. Selected project, filters, open tabs and unsaved edits stay inside SUSM. Preserve the mounted instance when switching panes. On workspace changes, cancel old requests, clear scoped views and load the new company mapping; never reuse data from the prior workspace.
  6. Fit the shell. Remove duplicate top navigation in embedded mode, scope CSS to the SUSM root and verify overlays stay in the intended pane. Release Angular views, kernel listeners, subscriptions and observers on unmount.
How it cooperates with other Sorye apps

SUSM requests platform actions through Hub APIs, kernel events or typed handoffs. It can offer a file to Drive or a document template to Protocolio without importing another app’s components. Introduce allowlisted handoff kinds and permission checks for each new action; current Sorye contracts do not automatically support arbitrary SUSM payloads.

Opening a document in Protocolio should carry a validated template or authorized record reference, not MongoDB credentials or a public R2 secret. Durable domain events still originate from successful Rodrigo operations; the UI can subscribe to authorized updates.

Acceptance before enabling it in the catalog
  • Open SUSM from the launcher, in each pane, beside another app; switch away and back without losing edits.
  • Reload a permitted deep link and use browser back/forward without leaving the intended Hub app or opening the wrong build.
  • Verify hidden apps do not steal focus or active-app identity, and repeated open/close leaves no leaked listeners.
  • Switch workspaces during an in-flight request; old company data never appears in the new context.
  • Check revoked access, unavailable remote, incompatible build and Rodrigo failure states.
  • Verify narrow panes, keyboard navigation, language switching, standalone entry and public feedback links.

Migration gates

Each phase needs its own verified ownership switch. Changing an environment URL alone cannot migrate company authorization, file references or PDF composition.

1 · Link identity and company boundaries

Register SUSM as an external Sorye application. Sorye’s current Auth.js login does not by itself make Sorye an OIDC provider. Add or integrate an authorization server, authorization-code flow with PKCE, registered redirects and scoped tokens.

Provision an audited mapping from existing company IDs to workspaces. Preserve existing user IDs; explicitly link accounts to verified Sorye subjects. Do not silently link an account from a claimed email. Invitations, disabled users, company roles and feature flags require parity checks. Keep public feedback links independent.

Gate: sign-in, sign-out, token expiry, removed-member rejection, wrong audience and cross-company access tests pass.

2 · Establish a typed SUSM domain in Rodrigo

Port one vertical slice, such as checklist-note updates, with request/response fixtures and existing authorization rules. Add signed Hub → Rodrigo contracts and dedicated MongoDB repositories. Requests never supply arbitrary collection names, Mongo filters or database credentials.

Keep the company aggregate initially. Enforce a workspace mapping in every repository operation, conditional updates and retry-safe command IDs. Inventory all current writers before switching that slice.

Gate: compare old/new API responses, stale updates, concurrent mutations, database outages and restart recovery. Quiesce the old writer for cutover; keep a reconciled rollback procedure.

3 · Bring existing R2 files under platform ownership

Inventory existing file metadata, bucket keys, public URLs and access expectations. Add Rodrigo-owned metadata pointing to the existing bytes. Verify checksums or another explicitly documented integrity baseline before treating import as complete.

Preserve current URLs until references are reconciled. New private files use authorized download APIs; do not assume a namespace prefix protects existing publicly reachable objects. Coordinate any public-access change separately.

Gate: uploads, download/preview, delete, quotas, failed multipart cleanup, cross-company denial and old-file compatibility pass. Remove SUSM-BE R2 credentials only after its final storage writer is cut over.

4 · Make events and work durable

A command requests a mutation; an event announces a committed fact. Store command receipts and outbox entries with the MongoDB mutation in a transaction on a suitable replica set. Verify topology first. Consumers deduplicate by event ID; delivery retries use bounded backoff and dead-letter handling.

Use shared Rodrigo leased jobs for long work. Cross-store delivery is at-least-once and reconciled. Record rendering states and file completion separately so a successful PDF cannot appear before its bytes are durable.

Gate: crashes before/after commit, duplicate requests, lost acknowledgements, consumer restart, lease expiry and poison events preserve correct results.

5 · Port reports to Protocolio and deploy independently

Retain the SUSM renderer for its existing workloads until template parity is established. Move one report type at a time. Compare page breaks, checklist sections, images, attachments, locale formatting and generated-document access.

Deploy Protocolio Node on the app VM with resource limits, health checks and bounded concurrency. Rodrigo owns persistent documents and MongoDB access; the renderer receives job inputs or scoped access to required resources. Sharing the VM does not require sharing a process or release.

Gate: representative golden PDFs, output-size limits, cancellation, missing images, renderer outage and restart recovery pass. Migrate without deleting existing documents or replacing MongoDB ownership prematurely.

Decisions to settle before cutover

Confirm whether one SUSM company maps to one Sorye team workspace, who may link an existing company, and how existing users are enrolled. Confirm the deployed MongoDB transaction capability and R2 public-access policy. These choices affect the migration; this document recommends one company per workspace but does not silently provision that mapping.
