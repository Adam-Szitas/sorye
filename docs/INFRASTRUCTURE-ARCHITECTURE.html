Why Forgejo? It provides Git hosting and integrated Actions workflows while delegating execution to separately installed Forgejo Runners. This maps well to separate VMs and limits the impact of build workloads. Gitea is a viable alternative, but choose one host deliberately; their Actions workflows are similar, not fully interchangeable. See the Forgejo Actions overview and runner administration guide.

2. Where services run

Proxmox manages virtual machines. Docker Compose runs services inside each VM. Network zones and credentials separate public traffic, application workloads, durable data and operations.

Proxmox cluster boundary

VMs are independently sized, backed up and replaceable. Use private VLANs/firewalls between these zones.

The important connections

  • Browser → ingressPublic HTTPS enters through one controlled edge.
  • Ingress → app poolPrivate routes distribute requests to healthy app instances.
  • App → PostgreSQL / S3Private service contracts keep metadata and bytes durable.
  • CI → registry → deployDeploy immutable image digests; CI has no Proxmox or production Docker socket access.
  • VMs and services → telemetryCollectors batch and forward measurements to a separate monitoring service.
  • Proxmox / DB / S3 → backupBackup data crosses to separate hardware and then an offsite account/location.

Start with Compose per VM. It is simple to operate and works with this layout. Compose does not schedule containers across VMs or provide cluster autoscaling. Add a cluster orchestrator only when measured cross-host scheduling needs justify its added operating burden.

3. Extend a component without coupling the whole system

The extension seam is the contract between services. Keep that contract stable, then add capacity or replace an implementation behind it.

Scale out

Hub and app workloads

Put stateless API instances behind ingress. Scale one micro-frontend’s asset delivery independently. Move CPU-heavy OCR and scheduled work into bounded worker pools.

Add capacity

Workers and queues

Add worker VMs and queue consumers independently. Bound concurrency, memory, retries and queue age; keep jobs durable so capacity can be increased without losing work.

Replace by contract

Database providers

Use Hub-owned repository interfaces and migrations. Add another database adapter only for a real deployment need; never silently split a workspace across providers on failure.

S3 contract

File storage

Keep the application on an S3-compatible API. Add storage nodes or move providers without changing app logic; verify consistency, versioning and restore behavior before cutover.

OCI contract

Images and deployment

Build OCI images and deploy immutable digests. A registry or deployment controller can be replaced independently if image naming, credentials and rollout health checks remain explicit.

One owner

VM and Docker management

Proxmox is authoritative for VMs; versioned Compose plus automation is authoritative for containers. A UI such as Portainer can help operators, but must not become a competing desired-state source.

Scale with evidence. Modular does not mean deploying every service separately from day one. Keep logical boundaries and resource limits from the start; add VM or replica boundaries when telemetry shows a component needs independent capacity or failure isolation.

4. See user experience and resource behavior

Give every app, worker, VM and data service a service name, environment, version, health check and telemetry path. A dashboard should connect a user-visible slowdown to the responsible component.

A practical stack is OpenTelemetry instrumentation and collectors, Prometheus-compatible metrics, Grafana dashboards, centralized logs/traces, and frontend error/performance reporting. Keep the monitoring control plane available when the application is unhealthy.

5. Backups that can be restored

A backup is useful only if it is isolated from the failure and deletion paths it must protect, and a restore has been demonstrated.

VM recovery

Proxmox Backup Server

Run PBS on separate hardware/storage. Use scoped credentials, encryption and retention. Replicate critical snapshots to another location/account.

Data recovery

Database + objects

Configure PostgreSQL point-in-time recovery and object versioning/replication. Set retention to match agreed recovery point and recovery time objectives.

Prove it

Restore drills

Schedule isolated restores and record duration, missing data checks and steps. Alert on missed backup windows, failed verification and insufficient retention.

Production app and CI credentials must not be able to delete backup history. Store recovery credentials separately and test the full path, including application startup and data integrity.

6. Add resources only where measurements point

This keeps the platform extensible while avoiding premature complexity and infrastructure spend.

Measure

Identify a sustained p95/p99, queue age, memory, I/O, error or saturation problem.

Isolate

Confirm which app, API, worker, DB, storage or VM owns the bottleneck.

Extend

Add replicas/resources at that seam, with health checks, limits and rollback.

Prove

Load-test the change and confirm user latency, reliability and cost improve.

Architecture proposal, not a claim about deployed state. Confirm actual VM inventory, Proxmox topology, VLANs, storage, DNS and backup targets before rollout.
