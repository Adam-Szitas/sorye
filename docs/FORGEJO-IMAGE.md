# Manual Forgejo image publishing

The `Publish Sorye frontend image` workflow in `.forgejo/workflows/publish-frontend.yml` has only a `workflow_dispatch` trigger. Pushing a commit makes it available for selection but does not build or publish an image. The workflow checks out the selected commit, verifies its SHA, builds the Hub Dockerfile from the repository root, and pushes one tag: `sha-<full 40-character commit SHA>`.

The image name is `<forgejo-host>/<owner>/<repository>:sha-<full-commit-sha>`, all lowercase. For example, `forgejo.example.com/sorye/sorye:sha-0123456789abcdef0123456789abcdef01234567`. Forgejo's container registry uses the Forgejo host and owner namespace. The workflow does not deploy or update Dockyard. Keep the SHA tag immutable in registry retention settings; Dockyard can also pin the digest printed by the registry after the push.

## Forgejo setup

1. Enable Actions for the repository. In repository Actions secrets, set `REGISTRY_USER` to a Forgejo account with package write access and `REGISTRY_TOKEN` to that account's personal access token with `write:package` scope. Use a token rather than an account password. Do not put registry credentials in repository variables or Dockyard build arguments.
2. In repository Actions variables, set each production remote entry URL: `NEXT_PUBLIC_DASHBOARD_REMOTE`, `NEXT_PUBLIC_CALENDAR_REMOTE`, `NEXT_PUBLIC_NOTES_REMOTE`, `NEXT_PUBLIC_TASKS_REMOTE`, `NEXT_PUBLIC_RELAY_REMOTE`, `NEXT_PUBLIC_PROTOCOLIO_REMOTE`, `NEXT_PUBLIC_CANVAS_REMOTE`, `NEXT_PUBLIC_DEVKIT_REMOTE`, `NEXT_PUBLIC_MESSENGER_REMOTE`, `NEXT_PUBLIC_OCR_REMOTE`, and `NEXT_PUBLIC_STUDIO_REMOTE`. Each should be the HTTPS URL of that app's `remoteEntry.js`. The workflow stops before publishing if any is empty. These URLs are embedded during the Next.js build; setting them only in Dockyard at runtime does not replace the browser bundle.
   The current workspace lockfile also references `vendor/protocolio-sdk-1.0.0.tgz`; commit that archive with the lockfile before running the workflow. The Docker context includes it so pnpm can install the selected commit without relying on files from a developer machine.
3. Confirm the repository has an online Forgejo runner advertising the `docker` label used in `runs-on`. The workflow's job image is `node:22-bookworm`; it installs the Docker CLI and checks `docker info` before building. A Docker runner's default configuration does **not** expose a daemon to job containers, so the runner administrator must configure a dedicated build daemon. Forgejo documents `container.docker_host: automount` for a local Unix socket or a Docker-in-Docker endpoint through `runner.envs.DOCKER_HOST` and `container.docker_host`. Prefer an isolated CI VM and dedicated daemon; access to a host Docker socket grants broad control of that host. Do not expose a production Docker socket to the runner. If the actual runner uses another label, change `runs-on` to that exact label before the first run.
4. Ensure the runner can reach Forgejo's HTTPS registry and that its Docker daemon trusts the registry certificate. A plain HTTP registry also needs Docker's insecure-registry configuration on the build daemon and on Dockyard's pull host; HTTPS is preferred.

To publish, open the repository's **Actions** tab in Forgejo, select **Publish Sorye frontend image**, click **Run workflow**, select the branch or tag containing the exact commit to publish, and run it. Copy the full image name and SHA tag from the successful job log. The job refuses to push if that SHA tag already exists; protect release history by also restricting package deletion and tag replacement in the registry.

## Dockyard app mapping

Keep the Sorye app mapping and deployment in Dockyard. Configure its image source as **pull an existing image**, using the full Forgejo image and `sha-<full SHA>` tag (or the pushed digest); do not enable an auto deploy on repository push or package publication. Give Dockyard a Forgejo package-read credential if the image is private. Set container port `3000`, publish it through the intended HTTPS ingress, and configure the Hub's production environment and persistent services there (`AUTH_URL`, auth secrets, `STORE_DRIVER=postgres`, `DATABASE_URL`, and any enabled storage or integration credentials). The production Hub must not use `AUTH_DEV_BYPASS`.

This image contains the Hub frontend and its Hub-native pages. Module Federation remotes remain separate app builds and origins; their `remoteEntry.js` URLs must be deployed and reachable by browsers before switching the Dockyard image. The Hub's OCR and Relay workers are separate processes and need their own Dockyard service definitions where those features are enabled. The workflow does not alter those services.

The public app landing pages remain accurate: this change adds a delivery path for the Hub image and does not alter app features or navigation behavior. The runtime behavior tree is unchanged for the same reason.
