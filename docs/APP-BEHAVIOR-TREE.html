Static reference for how a user moves through the Hub, how apps reach their handlers, where data is stored, and how OCR hands a matrix to Protocolio.

How to read it: arrows name the route or action that connects nodes. Node IDs match the handler index below each diagram. The diagrams are static SVG; this file has no scripts, controls, or external dependencies.

1. Open an app and retain its state

Hub resolves identity and the active workspace before showing the catalog. List reads then partition Personal and Work from the workspaces on that server session, without a client-supplied workspace id. Personal rows are returned only when that app is in the viewer's personal subscription (selected apps plus always-available apps). Team lists are not filtered by the personal package. Opening a row from the other section uses the authorized workspace switch. In Messenger, typing a name suggests a person in that channel's workspace; choosing one and sending notifies them in that Personal or Work scope. A personal ping is skipped when Messenger is not in the recipient's personal subscription. Contact, Catalog, SUSM, and ESPM are not member-data lists. Reports stays the active workspace's event charts.

Hub resolves identity and workspace before showing the catalog. Apps can be Hub-native, Module Federation remotes, or external iframe apps. Pane state and app-private state have different owners and lifetimes. Background state reads pause in hidden/offline tabs: notifications update on events with a 60-second safety refresh; standalone workspace state refreshes on focus/reconnect with a five-minute safety refresh. Event bursts are coalesced and requests do not overlap. In Postgres mode, OCR is submitted as a durable job. The mounted app polls authorized progress; if the user leaves, the worker still finishes the job and Hub notifies that user in that workspace. Opening the notice or returning to OCR shows the finished reading or the existing error. Local JSON development retains the direct analyze/continue path.

2. App requests, events, and handoffs

Apps use authenticated Hub APIs for shared data. The kernel gives each remote a constrained client. Hub validates input and workspace scope before a service/store handles it.

Tasks persists a typed board action with a stable id and payload in app-owned IndexedDB before calling Hub. Hub authorizes the signed-in user and active workspace, then Rodrigo commits the board and idempotency receipt in PostgreSQL. The queue clears only after a per-action committed or duplicate acknowledgement. Pending and failed counts expose Resend; conflicts stay queued for explicit reconciliation. Tasks' legacy PUT route returns 410 and stale localStorage boards are not imported. Notes and Calendar retain their existing whole-document behavior pending separate cutovers.

3. OCR matrices, Node analysis, and Protocolio

OCR has two reading paths: a browser matrix path for review/comparison/export and a Node PDF.js path that normalizes meaningful body rows into one continuous three-column table. In Postgres mode, Hub validates and queues the source file, a bounded worker processes it outside the interactive request, and the mounted OCR app polls job progress. Leaving OCR does not cancel the job. When the job completes or fails, Hub writes a notification for the submitting user in that workspace. Clicking it opens OCR on that analysis through the same open-app path as the launcher. Opening OCR again loads the latest job and shows the finished reading or the existing error instead of a stuck processing screen. While Qwen is running, the screen shows elapsed model time from the first model-request timestamp, excluding queue wait and PDF extraction. The normalized table scrolls inside a bounded region with a sticky header. Filename, stored ID and PDF type identify the document; unclear findings follow the data. The browser sends a selected matrix to Protocolio through a workspace handoff.

Production job path: POST /api/ocr/analyze returns a job ID. The Hub worker runs pnpm --filter @sorye/hub worker:ocr, renews its Postgres lease while processing and stores page rows before inference. Local pnpm dev starts that same worker when STORE_DRIVER=postgres. While OCR is mounted it polls GET /api/jobs/[id]; Hub verifies both workspace and submitting user. Leaving the app does not cancel the job. Completion or failure writes a Hub notification for that user only. GET /api/ocr/active is session-scoped and ignores a client workspace id. Local JSON mode continues to use the direct request path.

Rodrigo discovery boundary

Authenticated browser → Hub /api/backend/capabilities → server-derived user and workspace → signed method/path/body assertion → independent Rodrigo Rust service → verified HTTP v1 capabilities.

Platform administrator → Hub /api/backend/topology → session and admin authorization → signed Rodrigo topology request → validated provider ownership and stream limits. Responses are not cached. Tasks and Calendar support explicit per-workspace Rodrigo ownership after verified migration. Unmapped workspaces and Notes retain Hub storage.

Rodrigo implements optional PostgreSQL/MySQL/MongoDB document stores, Redis caching, S3-compatible storage and durable resumable document streams. Unconfigured providers report not_configured; dataReady requires all document owners and healthy configured dependencies. Unmapped app data stays in Hub; explicitly migrated Tasks and Calendar documents belong to Rodrigo. An unavailable or incompatible Rodrigo returns 503 through the discovery endpoints without changing data ownership.

Rodrigo private metrics listener → Prometheus → authenticated Grafana UI. Structured logs → redacting Alloy collector → separate Grafana Loki storage. These services and their deployment configuration live in the separate Rodrigo repository. Rodrigo contract and setup.

Rodrigo v2 action ownership

App → same-origin Hub API → server session, membership and enabled app → configured workspace/kind owner. Unmapped: existing Hub or workspace database. Frozen: Hub reads remain available; writes return 503 and keep the draft. Rodrigo: signed snapshot or conditional write → sole Rust document writer → revision translated using the verified import offset → app.

Stale writes return 409; outages return 503 without a Hub fallback. Deletions retain their revision when rendered empty. Legacy imports cannot resurrect deleted records. Invalid stored documents return 503 instead of a writable empty document. Malformed ownership configuration fails closed.

Tasks, Notes, Calendar, Canvas, Site editing, Storefront products, workspace profile name/read paths, and Messenger text/channel resources use Rodrigo v2 through Hub. Browser writes use scoped IndexedDB queues and clear only after durable acknowledgement. Their old resource writers are disabled. Messenger uses a channel-authorized timeline; image/blob sends and read receipts remain unavailable. Most other apps, Hub-native state, blobs, external jobs, event delivery, public Site reads, and Storefront orders remain uncovered. See the data contract and the switching runbook.

Administration console

Browser on sorye.app/admin or the retired /apps/operator → 307 to admin.sorye.app. Browser on admin.sorye.app → admin gateway allowlist → Hub middleware (admin host, allowlist, same-origin writes, no-store and frame-deny headers) → adminAccess (admin host, Auth.js session, isPlatformAdmin) → 404, login, "not a platform administrator", or the console. The redirect is not the protection; every page and API repeats the checks. Host-only cookies keep admin and customer sessions apart. Unknown hosts get 421 in production.
